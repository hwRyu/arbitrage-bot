# 실거래 준비와 운영

> 김프 헷지 전략만 실거래가 된다. 펀딩비 전략은 계속 페이퍼다.
> **실제 돈이 움직인다. 아래 순서를 건너뛰지 말 것.**

## 1. 구조: 페이퍼와 실거래는 같은 로직
```
엔진 (kimp/engine.py)          언제 진입·청산·리밸런싱할지          ← 모드와 상관없이 같음
  └ 브로커 (kimp/broker.py)     진입 3단계·되돌리기·청산 이어서·손익·송금·대조·안전장치  ← 같음
      └ 실행기                  주문 한 동작씩                       ← 여기만 다름
          페이퍼   PaperExecutor   (kimp/executor.py)      그 순간 호가로 체결 계산, 가짜 잔고
          드라이런 DryRunExecutor  (kimp/live_executor.py) 실제 잔고로 시작, 체결은 페이퍼처럼 계산, 주문 안 냄
          실거래   LiveExecutor    (kimp/live_executor.py) 실제 주문, 거래소 체결값·잔고
```
- 시뮬레이션도 같은 엔진·브로커를 쓴다. 구조를 바꾼 뒤 시뮬레이션 결과가 바꾸기 전과 한 줄도 다르지 않은 것을 확인했다 (거래 내역 전부 일치).
- 손익은 실거래에서 **거래소가 돌려준 실제 체결가·수량·수수료**로 계산한다.

| 모드 | 설정 | DB |
|---|---|---|
| 페이퍼 | `PAPER_TRADING=true` (기본) | `data/kimp.db` |
| 드라이런 | `PAPER_TRADING=false`, `LIVE_DRY_RUN=true` (기본) | `data/dryrun.db` |
| 실거래 | `PAPER_TRADING=false`, `LIVE_DRY_RUN=false`, `LIVE_CONFIRM=YES` | `data/live.db` |

## 2. 진입·청산이 실제로 어떻게 나가나
**진입 (버퍼 원화로 코인 FOK 를 먼저, 체결되면 USDT 매도와 숏을 동시에)** — 2026-10-30 부터.
그 전(10-26~30)은 USDT 매도 → 코인 FOK → 산 개수만큼 숏, 그 전(~10-26)은 숏 → USDT → 코인 순서였다.
0. **원화 버퍼**: 엔진이 업비트에 '가장 큰 포지션 크기 × `UPBIT_KRW_BUFFER_POSITIONS`(기본 2)' 만큼을 늘 원화로 둔다
   (계좌를 새로 받는 스캔마다 목표의 90% 아래면 USDT 를 팔아 채움, `[원화 버퍼] 채움` 로그). 버퍼 채우기는 포지션 다리가 아니라
   체결 기록(fills)에 남지 않고 잔고로만 센다. 진입·청산 도중(OPENING/CLOSING) 포지션이 있으면 그 스캔엔 안 채운다.
   버퍼가 모자란 채 진입 신호가 오면 그 자리에서 먼저 채운다 (그때만 예전처럼 USDT 매도가 코인보다 앞선다).
1. 업비트 XRP 매수 — 버퍼 원화로, 지정가, **전량 즉시 체결 아니면 취소**(Fill or Kill). 판단 → 거래소 도착이 USDT 매도 한 번
   (약 0.4초)만큼 빨라졌다.
   - **지정가 = 우리 수량이 닿는 마지막 매도 호가 줄 가격** (2026-10-29, docs/issues.md #3 A). 지정가는 '이 가격까지는 사겠다' 는
     상한이라 거래소는 싼 줄부터 채우고 체결 평균은 판단한 평균 그대로다. 예전처럼 평균가를 내림해 내면 두 줄에 걸칠 때 첫 줄
     물량만 쓸 수 있어 늘 놓쳤다. 예) 88.0원 3,000개 + 88.1원 1,000개를 사면 지정가 88.1원, 평균 88.025원.
   - **안전 확인**: 주문 직전에 앞쪽 싼 줄이 먼저 팔려 나가면 전부 마지막 줄 가격에 살 수도 있다. 그래서 진입 판단 때
     "전부 그 가격에 사도 진입 기준을 넘나" 를 함께 본다 (kimp/fok_sizing.py).
   - **진입 크기 상한** (`ENTRY_MAX_DEPTH_SHARE_PERCENT`, 기본 50, #3 B): '지정가 안쪽 물량'(전부 그 가격에 사도 기준을 넘는 가장
     비싼 매도 호가 줄까지의 물량 합) 중 이 %까지만 산다. 넘으면 숏 개수를 줄이고 `[진입 크기 줄임]` 로그를 남긴다. 남이 0.5초
     사이 일부를 먼저 사 가도 남은 물량으로 전량 체결될 여유다. 비율은 줄마다가 아니라 합에 건다. 크기를 먼저 안쪽 물량에 맞춘 뒤
     평균 김프를 보므로, 원래 크기로는 기준 밖 줄까지 먹어 안 되던 기회도 작게 잡는다.
   - 지정가 매수 개수 = 원화 ÷ 지정가 라서 (업비트가 지정가 × 개수만큼 원화를 묶는다) 실제로는 더 싸게 사고 원화가 조금 남는다
     (지정가와 평균의 차이만큼, 보통 0.1% 안팎). 남은 원화는 업비트 원화 잔고 자투리로 남고 자본에는 그대로 포함된다.
   - 취소되면 '진입 놓침' — **아무것도 한 게 없다** (USDT 도 숏도 안 건드림) → `ABORTED` / `ENTRY_MISSED`, 비용 0.
     (10-30 전에는 USDT 를 먼저 팔아 놓칠 때마다 왕복 0.175%, 15번에 −0.51 USDT 였다.) 2초(`FOK_RETRY_SEC`) 뒤 다시 판단한다.
   - 다리마다 `[판단→체결 가격 이동] #N COIN side | 판단 → 체결 | 주문 사이 가격 이동 x% 불리 (호가 소진 …)` (2026-10-30). 판단가는 판단 때 호가로
     우리 수량을 먹은 평균이라 호가 소진 몫은 이미 들어 있고, 판단 → 체결 차이는 거의 전부 그 사이(0.2~0.6초)의 **가격 이동**이다.
     예전에 '밀림' 이라 부르던 것의 정체 (BLEND #38 숏 닫기 +0.814%: 바이비트가 그 1분에 +2.5% 급등 중). 불리한 방향이 +.
   - 주문마다 `[주문 체결]`/`[지정가 미체결]` 끝에 **단계별 시간** `요청 0.41초 · 확인 조회 3회 1.21초 (첫 조회 wait) · 합계 1.62초`
     (요청 = 주문 요청 → 응답, 확인 = 끝날 때까지 0.25초 간격 상태 조회). 지연이 거래소 응답인지 우리 조회인지 여기서 가린다 (issues N4).
   - 지정가 주문마다 `[지정가 주문]` 로그 (지정가·수량·안쪽 물량·몇 줄·호가 3줄·체결 여부). 놓치면 `[진입 놓침]` 에 이유가 붙는다:
     두 칸 걸침 / 호가 이동 / 물량 부족 / 다시 충분 / 알 수 없음 (kimp/fok_trace.py, #3 C).
   - **신호 신뢰도 게이트** (2026-10-31, docs/filter.md): 김프가 기준 안으로 **막 들어온** 순간, 순손익이 목표를 **막 넘은** 순간은
     주문하지 않고 `[진입 대기] COIN | 김프 … ≤ 기준 … 이지만 신뢰도 0.10 (신호 0.3초째, 급변 뒤 판정 중) < 컷 0.70` /
     `[익절 대기] #N …` 을 남긴다 (10초에 한 줄). 신호가 되돌림 없이 유지되면 점수가 올라 약 2.7초(τ 2.5초) 뒤 주문하고,
     그 전에 꺼지면(틈) 아무 일도 없다. `[진입]`·`[익절 판단]` 끝에 그때의 신뢰도가 붙는다. 끄려면 `SIGNAL_FILTER_ENABLED=false`.
   - **거래소 조회는 판단 루프 밖에서** (2026-10-31, issues N7): 잔고·숏은 계좌 갱신 스레드가 2초마다 스냅샷으로, 펀딩비는 캐시 스레드가,
     하루 변동폭은 1시간마다 별도 스레드가 받는다. 판단은 그 값만 읽는다. 거래소가 응답을 안 줘 스냅샷이 `ACCOUNT_STALE_SEC`(10초)보다
     오래되면 `[계좌 조회 지연] … 신규 진입·숏 사라짐 판정 보류` (1분에 한 줄) 뒤 `[계좌 조회 복구]`. 갱신 스레드 자체의 실패는
     `[계좌 갱신 실패] bybit | …` (1분에 한 줄). 주문 직후에는 그 거래소 값이 낡았으므로 예전처럼 그 자리에서 받는다.
   - **경계 위 모드** (2026-10-31, docs/issues.md #6): 보유 중 업비트 가격이 호가 단위 경계를 넘어 한 칸 % ≥ 목표 % 가 되면
     `[경계 위 모드] #N COIN 시작 | … 한 칸 0.94% ≥ 목표 0.20%` (WARNING) 을 남기고, 익절 대신 `[경계 위 청산 대기/보류/판단]` 으로
     본전(펀딩비 받는 중)·최소 손해(내는 중: 순손익(수수료 제외) ≥ −다음 정산 펀딩비) 기준에 나온다. 청산 사유 `TICK_ZONE_EXIT`.
     경계 아래로 돌아오면 `[경계 위 모드] … 해제`. 진입 쪽은 `[진입 보류] COIN | 위쪽 경계 100원까지 2.7% < 보통 하루 변동폭 5.1%`
     (10분에 한 줄, 기록 `tick_zone_block`). 끄려면 `TICK_ZONE_ENABLED=false`.
   - 시장가 모드는 2026-10-29 제거: 업비트는 한 칸이 0.1~1% 라 한 칸만 밀려도 목표 이익 0.2% 를 넘는다 (CAP #12 140원 판단 → 141원 체결, 0.71%).
2. ‖ 3. 체결되면 **동시에** (서로 독립이라 기다릴 이유가 없다):
   2. 업비트 USDT/KRW 시장가 매도 — 코인에 쓴 원화(체결 금액 + 수수료)만큼 되채운다 → 버퍼가 원래 액수로. USDT 호가는 깊어서 밀림 0.
      호가가 1원 움직이면 몇백 원 빗나가는데, 그건 이 포지션의 USDT 매도 가격(`usdt_sold`·`entry_usdt_price_krw`)에 기록된다.
   3. 바이비트 XRP 숏 시장가 — **금액 헷징**: 숏 개수 = 코인 체결 금액(원) ÷ USDT 가격 ÷ 바이비트 가격 (= 코인 개수 × (1 + 진입 김프)).
      단방향 모드, 격리 마진. 크기 맞추기(`HEDGE_TOLERANCE_PERCENT`)도 금액으로 비교한다.

- 1번 실패(거절): 되돌릴 것 없음 → `ABORTED` / 3번(숏) 실패: 코인을 되팔고, 2번이 됐으면 그 원화로 USDT 를 되산다 → `ABORTED`
- 2번(USDT 매도)만 실패: 헷지(코인·숏)는 완성이라 되돌리지 않는다. `OPENING` 으로 두고 신규 진입을 막은 채 다음 스캔에 되채우기만
  다시 한다 (`[USDT 되채우기 실패]` CRITICAL → 되면 `[복구] … USDT 되채우기 완료` 뒤 `OPEN`)
- 되돌리기도 실패: `ERROR` + 텔레그램 긴급 알림 + **신규 진입 중단**. 거래소 앱에서 직접 정리해야 한다.
- 단계마다 체결을 DB 에 바로 저장한다. 중간에 프로그램이 꺼지면, 다시 켤 때 이어서 정리한다 (끝난 단계만 되돌림).

**청산**: 업비트 코인 매도 → 받은 원화로 USDT 매수 → 바이비트 숏 닫기 (reduceOnly)
- 익절: 코인 매도를 지정가 FOK 로 먼저 낸다. **지정가 = 우리 수량이 닿는 가장 싼 매수 호가 줄** (#3 A). 익절 기준은 목표 그대로이고
  (유동 여유는 2026-10-29 제거), 대신 **안전 확인**으로 "전부 그 줄 가격에 팔아도 목표를 넘나" 를 본다. 못 넘으면 팔지 않고
  `[익절 보류] … 전부 마지막 매수 호가 줄에 팔면 …` 뒤 다음 스캔에 다시 (`tp_worst_fail`). 익절은 크기 상한(B)이 없다 —
  코인과 숏을 같이 다 닫아야 해서 일부만 팔 수 없다. 전량 체결 안 되면 포지션을 그대로(OPEN) 두고 `[익절 보류]` 에 놓친 이유를 붙여
  2초 후 다시 판단. 체결되면 숏 닫기·USDT 매수로 이어진다. **손절·강제청산 가드·수동 청산은 시장가** (빠져나오는 게 우선)
- 어느 단계가 실패하면 `CLOSING` 으로 두고 다음 스캔에서 **남은 단계만** 다시 한다 (이미 판 코인을 또 팔지 않음).
- 봇 계산으로 강제청산 가격에 닿았는데 거래소에서 숏이 살아 있으면, 바로 시장가로 닫는다.

### 업비트 지정가 FOK 한눈에 보기 (2026-10-29, docs/issues.md #3)
**원칙: 기준 안 호가 줄까지만 산다.** "전부 그 줄 가격에 사도 진입 기준을 넘는" 매도 호가 줄까지를 '지정가 안쪽' 이라 하고,
그 밖의 줄에는 손대지 않는다. `ENTRY_MAX_DEPTH_SHARE_PERCENT` 는 그 안쪽 물량 가운데 **얼마까지 살지**만 정한다.

| 하는 일 | 무엇을 정하나 | 진입 매수 | 익절 매도 |
|---|---|---|---|
| A. 지정가 | 얼마까지 사고팔지 (상한·하한) | 우리 수량이 닿는 마지막 매도 호가 줄 | 우리 수량이 닿는 가장 싼 매수 호가 줄 |
| A. 안전 확인 | 최악에도 괜찮은가 | 전부 그 줄 가격에 사도 진입 기준 안 | 전부 그 줄 가격에 팔아도 목표 이상 (아니면 `tp_worst_fail`, 기다림) |
| B. 크기 상한 | 얼마나 살지 | 지정가 안쪽 물량 × `ENTRY_MAX_DEPTH_SHARE_PERCENT` | 없음 (코인·숏을 같이 다 닫아야 해서 일부만 못 판다) |
| C. 기록 | 왜 놓쳤나 | `[지정가 주문]`, `[진입 놓침] … 이유:` | `[지정가 주문]`, `[익절 보류] … 이유:` |

- 지정가는 '이 가격까지는' 이라는 상한이다. 거래소는 싼 줄부터 채우고 각 줄은 그 줄 가격에 체결된다.
  예) 지정가 88.1원으로 4,000개 → 88.0원 3,000개는 88.0원에, 88.1원 1,000개는 88.1원에 → 평균 88.025원.
- 비율은 줄마다가 아니라 안쪽 물량 **합**에 건다 (업비트 주문 하나는 가격 상한 하나와 수량 하나뿐).
- 크기를 먼저 안쪽 물량에 맞춘 뒤 평균 김프를 본다. 그래서 원래 크기로는 기준 밖 줄까지 먹어 못 들어가던 기회도 작게 잡는다.
- **호가 단위 경계 근처는 진입하지 않는다** (`ENTRY_TICK_BOUNDARY_MARGIN_PERCENT`, 기본 1%, 2026-10-30, docs/issues.md #4).
  매도 호가가 한 칸이 커지는 경계(100·1,000·10,000원 …) 아래 1% 안이거나 딱 경계면 보류한다. 예) 99.0~100원.
  스프레드 가드는 지금 호가 간격만 봐서 99.9 / 100원처럼 아래쪽이 아직 0.1원 칸이면 통과시키는데, 그 줄이 팔리면 다음 줄이
  101원(+1%)이라 주문이 닿기 전에 놓친다 (CAP 47초에 4번). 경계 위(101원 이상)는 왕복 호가가 넓어 스프레드 가드가 막는다.

**예시** — 매도 호가 88.0원 3,000개 / 88.1원 5,000개 / 88.2원 10,000개. 88.1원까지 기준 안, 88.2원은 기준 밖 → 안쪽 물량 8,000개

| 사려던 양 | 설정 50 (기본) | 설정 100 | 2026-10-29 전 |
|---|---|---|---|
| 5,680개 (안쪽 안) | 4,000개로 줄임, 지정가 88.1원 | 5,680개 그대로, 지정가 88.1원 | 지정가 88.0원(평균 내림) → 두 줄에 걸쳐 늘 놓침 |
| 12,000개 (88.2원 줄까지 먹음) | 4,000개로 줄임, 지정가 88.1원 | 8,000개로 줄임, 지정가 88.1원 | 평균 김프만 봄: 기준 밖이면 안 들어감, 기준 안이면 88.2원 줄까지 사려 함 |

- 50 의 뜻: 누가 0.5초 사이 88.0원 3,000개를 먼저 사 가도 88.1원 5,000개로 우리 4,000개가 다 채워진다 (여유분).
  100 이면 같은 상황에서 남은 5,000개로 5,680개를 못 채워 놓친다 — 여유분이 없다. 다만 '기준 안 줄까지만' 원칙은 100 이어도 그대로다.
- 포지션이 약 2.7만 원일 때는 맨 앞 줄 물량이 훨씬 커서 50 이든 100 이든 실제로 줄어드는 일은 거의 없다. 차이는 규모를 키울 때 난다.
- 지정가 매수 개수 = 원화 ÷ 지정가 (업비트가 지정가 × 개수만큼 원화를 묶는다). 두 줄에 걸쳐 더 싸게 사면 원화가 조금 남는다
  (보통 0.1% 안팎, 업비트 원화 잔고로 남고 자본에 포함).

### 레그 리스크 (한쪽만 체결) 대비
| 상황 | 처리 |
|---|---|
| 진입 때 부분 체결로 코인 **개수**와 숏 **개수**가 1% 넘게 다름 (`HEDGE_TOLERANCE_PERCENT`) | 큰 쪽을 줄여 맞춤. 숏이 많으면 남는 숏 닫기, 코인이 많으면 남는 코인 팔기. 못 쓴 원화는 USDT 로 되삼. (숏을 산 코인 개수로 치므로 보통 여기 올 일이 없다) |
| 청산 때 일부만 체결 | '목표 양에 닿았나' 로 판단해서 남은 양만 다시 주문 (최대 3번, 그래도 남으면 다음 스캔) |
| 주문 응답이 끊김 | 주문마다 붙인 추적번호(바이비트 orderLinkId, 업비트 identifier)로 조회: 들어가 있으면 그대로 진행, 없으면 실패 처리 |
| 응답 끊김 + 조회도 안 됨 | 추측하지 않고 멈춤 (그 포지션은 그대로, 신규 진입 중단) → 다음 스캔마다 다시 조회해서 이어서 처리 |
| 20초 안에 안 끝나는 주문 | 취소 → 다시 조회 → 체결된 만큼으로 진행 (남은 양은 위 규칙으로) |
| 주문 도중 프로그램이 꺼짐 | 주문 '전에' 추적번호를 DB 에 먼저 적어 두므로, 다시 켜면 조회해서 결과를 채우고 이어서 |

- 맞추는 비용(열었다 바로 닫은 부분의 수수료·호가 간격)은 **그 포지션의 진입 비용**에 들어가서, 보유 중 순손익·청산 판단·최종 손익에 그대로 반영된다.
  예) 숏 50 USDT 중 5 USDT 를 닫아 맞춤 → 비용 약 0.003 USDT 가 바이비트 진입 비용에 더해짐
- 맞추기마저 실패하면 실제 수량 그대로 OPEN 으로 두고 정상 청산 + 긴급 알림 (ERROR 로 두면 봇이 청산을 못 하므로)
- 남는 위험: 세 주문 사이(수백 ms~1초)에 가격이 움직이는 것. 진입 전 슬리피지 확인(0.3%)으로 줄이지만 없앨 수는 없다.

### 한 번만 돌리기 (ONE_SHOT) — 기본은 꺼짐
| 설정 | 기본 | 뜻 |
|---|---|---|
| `ONE_SHOT` | `false` | `true` 면 포지션을 **하나만** 잡고, 청산되면 봇이 스스로 종료 |
| `ONE_SHOT_MAX_HOURS` | `0` | 이 시간을 넘겨도 목표·손절에 닿지 않으면 시장가로 정리 (청산 사유 `TIMEOUT`). `0` = 무제한 |

- 여러 코인이 동시에 조건을 만족해도 **하나만** 잡는다.
- 이미 열린 포지션이 있으면 그것만 끝까지 관리하고 종료한다 (새로 잡지 않음).
- `ERROR`(되돌리기도 실패) 면 그 상태로 멈추고 긴급 안내를 찍는다 — 사람이 거래소에서 직접 정리해야 한다.
- 페이퍼·드라이런에서도 쓸 수 있다 (한 바퀴만 보고 싶을 때). 로컬 화면 '페이퍼 봇' 탭에도 체크박스가 있다.
- **끄면(기본) 평소처럼 계속 돈다.** 전략 로직은 바뀌지 않는다.

## 4. 자동 송금 (리밸런싱)
- 언제: 청산 후 양쪽 비율이 10%p 넘게 깨졌을 때 / 진입하려는데 한쪽이 모자랄 때 (맞춰도 못 들어가면 안 보냄)
- `AUTO_TRANSFER_ENABLED=false`(기본)면 **알림만** 하고 직접 보낸다. true 면 봇이 출금한다.
- 네트워크는 거래소마다 이름이 다르다: 트론 = 업비트 `UPBIT_TRANSFER_NETWORK=TRX` / 바이비트 `BYBIT_TRANSFER_NETWORK=TRC20`. **둘이 같은 체인인지 꼭 확인** (다른 체인으로 보내면 돈을 잃는다)
- 업비트 → 바이비트: 업비트 출금 API (업비트 이름 net_type)
- 바이비트 → 업비트: 통합계좌 → 펀딩 계좌로 옮긴 뒤 출금
- 받는 쪽 입금 내역에 금액이 맞는 '완료' 입금이 보이면 도착. 그동안 그 돈은 받는 쪽 자본으로 치고, 또 보내지 않는다.
- `TRANSFER_MIN_USDT`(10) 미만은 안 보냄, `TRANSFER_MAX_USDT_PER_DAY`(1,000) 까지, `TRANSFER_ALERT_MINUTES`(60) 넘게 안 오면 긴급 알림
### 업비트 출금지연제 (2026-10-22 실제로 막혔다)
**원화를 입금하면 그 금액 상당의 코인을 24시간 동안 다른 곳으로 보낼 수 없다.** 사고파는 건 된다.
- 그날 원화 200만원을 입금하고 846 USDT 송금을 시도했더니 거절됐다:
  `출금 가능한 수량을 초과하였습니다. 출금지연제 적용(공지 참고)에 따라 24시간 이내 입금하신 원화 입금액 상당의 코인은 출금 가능 수량에서 제외됩니다.`
- 1 USDT 는 통과했다 (잠긴 금액을 넘는 여유분만 나간다). **수동·API 모두 같은 규정**이다.
- `python -m kimp.live_check` 가 '업비트 출금 가능 상태' 로 미리 알려준다 (남은 시간까지).
- 봇은 이 거절을 **연속 실패로 세지 않고** 10분 뒤 다시 시도한다 (`broker.POLICY_RETRY_SEC`).
  켜둔 채로 두면 24시간이 지난 뒤 자동으로 송금된다.

- **확인 필요:** 업비트 ↔ 바이비트 트래블룰은 '계정주 확인 연동' 방식으로 알려져 있다 (2026-08 정리 기준, 업비트 공지로 직접 확인). 바이비트 → 한국 거래소 출금 때 수취인 정보를 요구할 수 있다. **첫 송금은 소액으로 손으로 한 번 해보고** 자동을 켤 것.

## 5. 준비 순서
1. **서버**: 업비트 키는 등록한 IP 에서만 동작 → 고정 IP 가 있는 곳에서 돌린다 ([deploy.md](deploy.md))
2. **업비트 Open API 키**: 자산조회 / 주문조회 / 주문하기 (자동 송금이면 + 출금하기, 입금조회, 출금조회). 서버 IP 등록
   - 자동 송금이면: Open API 관리 > **출금 허용 주소**에 바이비트 USDT 입금 주소(`BYBIT_TRANSFER_NETWORK`, 트론이면 TRC20) 등록
3. **바이비트 API 키**: 통합계좌(UTA), 선물(Contract) 주문 권한 (자동 송금이면 + 출금 권한). IP 제한
   - 자동 송금이면: 출금 주소록(화이트리스트)에 업비트 USDT 입금 주소 등록
   - 봇이 시작할 때 코인마다 **단방향 모드 + 격리 마진 + BYBIT_LEVERAGE** 로 맞춘다
4. **텔레그램**: @BotFather 로 봇 만들기 → 토큰. 봇에게 말 걸고 `https://api.telegram.org/bot<토큰>/getUpdates` 에서 chat.id
5. `.env` 작성 (`.env.example` 의 '실거래' 부분)
6. `python3 -m kimp.live_check` → ❌ 가 없을 때까지 (읽기만 함)
7. **드라이런** `PAPER_TRADING=false`, `LIVE_DRY_RUN=true` 로 하루 이상: `[드라이런] 실제였다면 …` 로그와 텔레그램 확인
8. **첫 실거래는 '한 번만 돌리기' 로** — 포지션 하나만 잡고 청산되면 봇이 스스로 종료한다
   ```powershell
   $env:PAPER_TRADING="false"; $env:LIVE_DRY_RUN="false"; $env:LIVE_CONFIRM="YES"
   $env:ONE_SHOT="true"; $env:ONE_SHOT_MAX_HOURS="6"     # 6시간 안에 목표에 못 닿으면 정리하고 끝
   $env:MAX_POSITION_USDT="20"; $env:MAX_OPEN_POSITIONS="1"
      .\.venv\Scripts\python.exe main.py
   ```
   끝나면 **점검 요약**이 찍힌다 (체결 6건의 개수·평균가·수수료, 손익 구성, 확인할 것 4가지).
   실제 주문을 내본 적이 없으니 이 한 바퀴로 전 과정을 확인한다.
   - 체결 내역이 거래소 앱과 같은지 (개수·평균가·수수료)
   - 양쪽 잔고가 예상대로인지 (바이비트 포지션이 0 인지)
   - 상태가 `CLOSED` 인지 (`ABORTED`·`ERROR` 면 아래 6번대로 정리)
9. 깨끗하면 `ONE_SHOT` 을 끄고 소액으로 계속 돌린다 (`MAX_POSITION_USDT=20~50`, `MAX_OPEN_POSITIONS=1`).
   문제없으면 크기와 개수를 천천히 늘린다

## 6. 운영 중
- 텔레그램 알림: 진입·청산·송금·경고가 자동으로 온다 (⚠️ 경고, 🚨 긴급). 매일 9시에 요약.
- 텔레그램 명령

| 명령 | 하는 일 |
|---|---|
| `/status` | 잔고·포지션·오늘 손익·진입 가능 여부 |
| `/premium` | 지금 김프 (가운데·진입·청산, **기준까지 몇 %p 남았나**, 호가 간격, 펀딩비) |
| `/close` | 들고 있는 포지션 **강제 청산 + 신규 진입 중단** (`/close` 전부, `/close CAP,SEI` 골라서). 청산 사유 `MANUAL`. 다시 돌리려면 `/resume` |
| `/stop` | **신규 진입만** 중단 (청산·강제청산 감시·송금은 계속) |
| `/resume` | 재개 (`/stop`·연속 실패 횟수를 풀고, 비상정지 파일 `data/STOP` 이 있으면 지운다 — 서버에 못 들어가도 텔레그램으로 재개) |
| `/collect` | 시세 수집 현황. `/collect start 40` 으로 켜고 `/collect stop` 으로 끈다 |
| `/help` | 명령 목록 |

- **`/close` 는 신규 진입도 함께 막는다** (`/stop` 과 같은 효과). 사람이 정리하라고 했는데 김프가
  여전히 기준 아래라서 같은 스캔에서 다시 들어가면 뜻과 다르기 때문이다. 다시 돌리려면 `/resume`.
- `/close` 는 요청만 적어두고 **다음 스캔에서 엔진이 청산한다** (텔레그램 스레드가 포지션을 직접
  건드리면 엔진과 충돌하기 때문이다). 보통 3초 안에 처리된다.
- `ERROR` 포지션이 생기면: 거래소 앱에서 그 코인의 업비트 코인·바이비트 숏을 확인해 직접 정리 → DB 에서 그 포지션 상태를 `ABORTED` 나 `CLOSED` 로 고친 뒤 재시작
- 거래소에서 **손으로 주문하지 말 것** (대조 불일치로 신규 진입이 멈춘다). 봇이 들고 있는 코인 말고 다른 코인은 괜찮다.
- 끄기: Ctrl+C (또는 `systemctl stop`). 열린 포지션은 DB 에 남아서 다시 켜면 이어서 관리한다.

- 하는 일: `logs/bot.log` 를 꼬리 따라가며 진입·청산·오류·웹소켓 끊김을 보고, `tools/monitor/resource_watch.sh` 로 1분마다 메모리·스레드·핸들을 `logs/resource_watch.csv` 에 적는다. 청산이 나면 DB 에서 **판단 순손익 대비 실제**, 다리별 밀림, `판단 → 전송 ms` 를 뽑아 보고한다.
- 부르기: Claude Code 에서 "봇 모니터링 붙여줘" / "bot-monitor 서브에이전트로 감시해" 라고 하면 된다. 사건이 나거나 정한 시간(기본 6시간)이 지나면 보고하고 끝나므로 계속 보려면 다시 띄운다.
- 하지 않는 일: 봇 중단·재기동, 파일 수정, 거래소 API 호출. 조치는 사람이(또는 메인 Claude 가) 한다.
- 자원 감시만 따로 보려면 터미널에서 `bash tools/monitor/resource_watch.sh` (윈도우 Git Bash 전용, 봇과 별개 프로세스).

## 7. 아직 안 된 것 / 주의
- 펀딩비는 실거래에서도 '예고 비율 × 숏 금액' 추정으로 기록한다 (실제 잔고에는 거래소가 반영하므로 비율 계산은 맞음).
- 실제 키로만 확인 가능한 것: 업비트 출금 `net_type`·허용 주소, 바이비트 계좌 이동·출금, 트래블룰, 격리 마진 설정 응답, 실제 체결값
- 거래량이 작은 코인: 업비트 코인 진입·익절은 지정가 FOK 라 판단보다 나쁘게 체결되지 않지만, 호가가 얇으면 진입 크기가 줄거나
  (`ENTRY_MAX_DEPTH_SHARE_PERCENT`) 놓침이 잦아진다. 맨 앞 호가보다 평균이 `MAX_SLIPPAGE_PERCENT`(0.3%) 넘게 나쁘면 진입하지 않는다.
  손절·가드·수동 청산은 시장가라 얇은 호가에서 밀릴 수 있다.
