# 실거래 준비와 운영

> 김프 헷지 전략만 실거래가 된다. 펀딩비 전략은 계속 페이퍼다.
> **실제 돈이 움직인다. 아래 순서를 건너뛰지 말 것.**

## 1. 구조: 페이퍼와 실거래는 같은 로직
```
엔진 (kimp/engine.py)          언제 진입·청산·리밸런싱할지          ← 모드와 상관없이 같음
  └ 브로커 (kimp/broker.py)     진입 3단계·되돌리기·청산 이어서·손익·송금·대조·안전장치  ← 같음
      └ 실행기                  주문 한 동작씩                       ← 여기만 다름
          페이퍼   PaperExecutor   (kimp/executor.py)      그 순간 호가로 체결 계산, 가짜 잔고
          드라이런 DryRunExecutor  (kimp/live_executor.py) 실제 잔고로 시작, 체결은 페이퍼처럼 계산, 주문 안 냄
          실거래   LiveExecutor    (kimp/live_executor.py) 실제 주문, 거래소 체결값·잔고
```
- 시뮬레이션도 같은 엔진·브로커를 쓴다. 구조를 바꾼 뒤 시뮬레이션 결과가 바꾸기 전과 한 줄도 다르지 않은 것을 확인했다 (거래 내역 전부 일치).
- 손익은 실거래에서 **거래소가 돌려준 실제 체결가·수량·수수료**로 계산한다.

| 모드 | 설정 | DB |
|---|---|---|
| 페이퍼 | `PAPER_TRADING=true` (기본) | `data/kimp.db` |
| 드라이런 | `PAPER_TRADING=false`, `LIVE_DRY_RUN=true` (기본) | `data/dryrun.db` |
| 실거래 | `PAPER_TRADING=false`, `LIVE_DRY_RUN=false`, `LIVE_CONFIRM=YES` | `data/live.db` |

## 2. 진입·청산이 실제로 어떻게 나가나
**진입 (바이비트 먼저)**
1. 바이비트 XRP 숏 시장가 (단방향 모드, 격리 마진)
2. 업비트 USDT/KRW 시장가 매도 (숏 금액만큼 USDT)
3. 업비트 XRP 시장가 매수 (받은 원화 ÷ (1 + 수수료율))

- 2번 실패: 숏을 닫는다 / 3번 실패: 받은 원화로 USDT 를 되사고 숏을 닫는다 → `ABORTED`
- 되돌리기도 실패: `ERROR` + 텔레그램 긴급 알림 + **신규 진입 중단**. 거래소 앱에서 직접 정리해야 한다.
- 단계마다 체결을 DB 에 바로 저장한다. 중간에 프로그램이 꺼지면, 다시 켤 때 이어서 정리한다 (끝난 단계만 되돌림).

**청산**: 업비트 코인 매도 → 받은 원화로 USDT 매수 → 바이비트 숏 닫기 (reduceOnly)
- 어느 단계가 실패하면 `CLOSING` 으로 두고 다음 스캔에서 **남은 단계만** 다시 한다 (이미 판 코인을 또 팔지 않음).
- 봇 계산으로 강제청산 가격에 닿았는데 거래소에서 숏이 살아 있으면, 바로 시장가로 닫는다.

### 레그 리스크 (한쪽만 체결) 대비
| 상황 | 처리 |
|---|---|
| 진입 때 부분 체결로 양쪽 금액이 1% 넘게 다름 (`HEDGE_TOLERANCE_PERCENT`) | 큰 쪽을 줄여 맞춤. 숏이 크면 남는 숏 닫기, 코인이 많으면 남는 코인 팔기. 못 쓴 원화는 USDT 로 되삼 |
| 청산 때 일부만 체결 | '목표 양에 닿았나' 로 판단해서 남은 양만 다시 주문 (최대 3번, 그래도 남으면 다음 스캔) |
| 주문 응답이 끊김 | 주문마다 붙인 추적번호(바이비트 orderLinkId, 업비트 identifier)로 조회: 들어가 있으면 그대로 진행, 없으면 실패 처리 |
| 응답 끊김 + 조회도 안 됨 | 추측하지 않고 멈춤 (그 포지션은 그대로, 신규 진입 중단) → 다음 스캔마다 다시 조회해서 이어서 처리 |
| 20초 안에 안 끝나는 주문 | 취소 → 다시 조회 → 체결된 만큼으로 진행 (남은 양은 위 규칙으로) |
| 주문 도중 프로그램이 꺼짐 | 주문 '전에' 추적번호를 DB 에 먼저 적어 두므로, 다시 켜면 조회해서 결과를 채우고 이어서 |

- 맞추는 비용(열었다 바로 닫은 부분의 수수료·호가 간격)은 **그 포지션의 진입 비용**에 들어가서, 보유 중 순손익·청산 판단·최종 손익에 그대로 반영된다.
  예) 숏 50 USDT 중 5 USDT 를 닫아 맞춤 → 비용 약 0.003 USDT 가 바이비트 진입 비용에 더해짐
- 맞추기마저 실패하면 실제 수량 그대로 OPEN 으로 두고 정상 청산 + 긴급 알림 (ERROR 로 두면 봇이 청산을 못 하므로)
- 남는 위험: 세 주문 사이(수백 ms~1초)에 가격이 움직이는 것. 진입 전 슬리피지 확인(0.3%)으로 줄이지만 없앨 수는 없다.

### 한 번만 돌리기 (ONE_SHOT) — 기본은 꺼짐
| 설정 | 기본 | 뜻 |
|---|---|---|
| `ONE_SHOT` | `false` | `true` 면 포지션을 **하나만** 잡고, 청산되면 봇이 스스로 종료 |
| `ONE_SHOT_MAX_HOURS` | `0` | 이 시간을 넘겨도 목표·손절에 닿지 않으면 시장가로 정리 (청산 사유 `TIMEOUT`). `0` = 무제한 |

- 여러 코인이 동시에 조건을 만족해도 **하나만** 잡는다.
- 이미 열린 포지션이 있으면 그것만 끝까지 관리하고 종료한다 (새로 잡지 않음).
- `ERROR`(되돌리기도 실패) 면 그 상태로 멈추고 긴급 안내를 찍는다 — 사람이 거래소에서 직접 정리해야 한다.
- 페이퍼·드라이런에서도 쓸 수 있다 (한 바퀴만 보고 싶을 때). 로컬 화면 '페이퍼 봇' 탭에도 체크박스가 있다.
- **끄면(기본) 평소처럼 계속 돈다.** 전략 로직은 바뀌지 않는다.

## 3. 안전장치 (모든 모드 같은 로직)
| 설정 | 실거래 기본 | 뜻 |
|---|---|---|
| `LIVE_CONFIRM=YES` | 필수 | 이게 없으면 실제 주문 모드로 안 켜진다 |
| `MAX_POSITION_USDT` | 50 | 포지션 하나 최대 금액 |
| `DAILY_LOSS_LIMIT_USDT` | 10 | 오늘(한국 시간) 확정 손실이 넘으면 그날 신규 진입 중단 |
| `MAX_CONSECUTIVE_FAILURES` | 3 | 주문 연속 실패 시 신규 진입 중단 (`/resume` 으로 재개) |
| `STOP_FILE` | `data/STOP` | 이 파일을 만들면 신규 진입 중단, 지우면 재개 (`touch data/STOP`) |
| `RECONCILE_INTERVAL_SEC` | 600 | 10분마다 거래소 실제 숏·코인 개수와 DB 비교. 다르면 신규 진입 중단 |

막혀도 **가진 포지션 관리·청산은 계속**한다.

## 4. 자동 송금 (리밸런싱)
- 언제: 청산 후 양쪽 비율이 10%p 넘게 깨졌을 때 / 진입하려는데 한쪽이 모자랄 때 (맞춰도 못 들어가면 안 보냄)
- `AUTO_TRANSFER_ENABLED=false`(기본)면 **알림만** 하고 직접 보낸다. true 면 봇이 출금한다.
- 네트워크는 거래소마다 이름이 다르다: 트론 = 업비트 `UPBIT_TRANSFER_NETWORK=TRX` / 바이비트 `BYBIT_TRANSFER_NETWORK=TRC20`. **둘이 같은 체인인지 꼭 확인** (다른 체인으로 보내면 돈을 잃는다)
- 업비트 → 바이비트: 업비트 출금 API (업비트 이름 net_type)
- 바이비트 → 업비트: 통합계좌 → 펀딩 계좌로 옮긴 뒤 출금
- 받는 쪽 입금 내역에 금액이 맞는 '완료' 입금이 보이면 도착. 그동안 그 돈은 받는 쪽 자본으로 치고, 또 보내지 않는다.
- `TRANSFER_MIN_USDT`(10) 미만은 안 보냄, `TRANSFER_MAX_USDT_PER_DAY`(1,000) 까지, `TRANSFER_ALERT_MINUTES`(60) 넘게 안 오면 긴급 알림
- **확인 필요:** 업비트 ↔ 바이비트 트래블룰은 '계정주 확인 연동' 방식으로 알려져 있다 (2026-08 정리 기준, 업비트 공지로 직접 확인). 바이비트 → 한국 거래소 출금 때 수취인 정보를 요구할 수 있다. **첫 송금은 소액으로 손으로 한 번 해보고** 자동을 켤 것.

## 5. 준비 순서
1. **서버**: 업비트 키는 등록한 IP 에서만 동작 → 고정 IP 가 있는 곳에서 돌린다 ([deploy.md](deploy.md))
2. **업비트 Open API 키**: 자산조회 / 주문조회 / 주문하기 (자동 송금이면 + 출금하기, 입금조회, 출금조회). 서버 IP 등록
   - 자동 송금이면: Open API 관리 > **출금 허용 주소**에 바이비트 USDT 입금 주소(`BYBIT_TRANSFER_NETWORK`, 트론이면 TRC20) 등록
3. **바이비트 API 키**: 통합계좌(UTA), 선물(Contract) 주문 권한 (자동 송금이면 + 출금 권한). IP 제한
   - 자동 송금이면: 출금 주소록(화이트리스트)에 업비트 USDT 입금 주소 등록
   - 봇이 시작할 때 코인마다 **단방향 모드 + 격리 마진 + BYBIT_LEVERAGE** 로 맞춘다
4. **텔레그램**: @BotFather 로 봇 만들기 → 토큰. 봇에게 말 걸고 `https://api.telegram.org/bot<토큰>/getUpdates` 에서 chat.id
5. `.env` 작성 (`.env.example` 의 '실거래' 부분)
6. `python3 -m kimp.live_check` → ❌ 가 없을 때까지 (읽기만 함)
7. **드라이런** `PAPER_TRADING=false`, `LIVE_DRY_RUN=true` 로 하루 이상: `[드라이런] 실제였다면 …` 로그와 텔레그램 확인
8. **첫 실거래는 '한 번만 돌리기' 로** — 포지션 하나만 잡고 청산되면 봇이 스스로 종료한다
   ```powershell
   $env:PAPER_TRADING="false"; $env:LIVE_DRY_RUN="false"; $env:LIVE_CONFIRM="YES"
   $env:ONE_SHOT="true"; $env:ONE_SHOT_MAX_HOURS="6"     # 6시간 안에 목표에 못 닿으면 정리하고 끝
   $env:MAX_POSITION_USDT="20"; $env:MAX_OPEN_POSITIONS="1"
      .\.venv\Scripts\python.exe main.py
   ```
   끝나면 **점검 요약**이 찍힌다 (체결 6건의 개수·평균가·수수료, 손익 구성, 확인할 것 4가지).
   실제 주문을 내본 적이 없으니 이 한 바퀴로 전 과정을 확인한다.
   - 체결 내역이 거래소 앱과 같은지 (개수·평균가·수수료)
   - 양쪽 잔고가 예상대로인지 (바이비트 포지션이 0 인지)
   - 상태가 `CLOSED` 인지 (`ABORTED`·`ERROR` 면 아래 6번대로 정리)
9. 깨끗하면 `ONE_SHOT` 을 끄고 소액으로 계속 돌린다 (`MAX_POSITION_USDT=20~50`, `MAX_OPEN_POSITIONS=1`).
   문제없으면 크기와 개수를 천천히 늘린다

## 6. 운영 중
- 텔레그램: 진입·청산·송금·경고가 온다. `/status` 현황, `/stop` 신규 진입 중단, `/resume` 재개, 매일 9시 요약
- `ERROR` 포지션이 생기면: 거래소 앱에서 그 코인의 업비트 코인·바이비트 숏을 확인해 직접 정리 → DB 에서 그 포지션 상태를 `ABORTED` 나 `CLOSED` 로 고친 뒤 재시작
- 거래소에서 **손으로 주문하지 말 것** (대조 불일치로 신규 진입이 멈춘다). 봇이 들고 있는 코인 말고 다른 코인은 괜찮다.
- 끄기: Ctrl+C (또는 `systemctl stop`). 열린 포지션은 DB 에 남아서 다시 켜면 이어서 관리한다.

## 7. 아직 안 된 것 / 주의
- 펀딩비는 실거래에서도 '예고 비율 × 숏 금액' 추정으로 기록한다 (실제 잔고에는 거래소가 반영하므로 비율 계산은 맞음).
- 실제 키로만 확인 가능한 것: 업비트 출금 `net_type`·허용 주소, 바이비트 계좌 이동·출금, 트래블룰, 격리 마진 설정 응답, 실제 체결값
- 거래량이 작은 코인은 시장가로 밀린다. `MAX_SLIPPAGE_PERCENT`(0.3%) 보다 밀릴 것 같으면 진입하지 않는다.
